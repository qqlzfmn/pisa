# 014 · 运行状态与小时巡检（pisa status）

- 状态：implemented
- 关联：003（看护进程与退出码）、004（探针的「失败才说话」先例）、009（周期触发）
- 依赖：无

## 1. 问题

pisa 是否活着只能靠人读 `~/Library/Logs/pisa.launchd.log`：进程半夜挂掉无人知道；白天又缺一个「现在到底好不好」的单一判断，于是反复翻日志刷屏。看护进程只在进程退出后重启，进程卡死（心跳停止、事件循环阻塞）完全检测不到。

需要两个能力：一个能被脚本与 launchd 消费的退出码，用来判断「正常 / 需重启 / 部件坏了 / 还没配好」；一个每小时跑一次、只在异常时才说话的巡检。

## 2. 目标

- `pisa status` 一条命令给出结论，退出码即结论
- 每小时巡检一次；正常时完全不输出、不推送
- 同一个问题只通知一次；恢复正常后清零，下次再坏重新通知
- 卡死也能发现：判断依据是守护进程持续写出的心跳，而不是进程是否存在

## 3. 用户故事

### US-1 脚本判断健康

作为运维，我执行 `pisa status`，按退出码分支：`0` 继续，`1` 重启进程，`2` 修部件，`3` 补配置。

### US-2 半夜挂了有人知道

作为维护者，守护进程凌晨挂掉后，下一小时的巡检推送一条「需重启」，我在早上看到，不用整夜盯日志。

### US-3 不刷屏

作为维护者，同一个问题持续存在时，巡检只通知第一次；修好之后记录清零，下次再坏重新通知。

### US-4 还没配好不计为故障

作为新用户，我复制了示例配置但还没填仓库路径，`pisa status` 返回 `3` 并指出缺什么，而不是误报「需重启」。

## 4. 需求

| ID | 需求 |
| --- | --- |
| FR-001 | `pisa status` 输出一段人类可读报告，并以退出码表达结论：`0` 正常 / `1` 需重启 / `2` 部件错误 / `3` 待配置 |
| FR-002 | `0`：配置齐备、部件可用、心跳新鲜 |
| FR-003 | `1`：配置与部件没有明确错误，但心跳缺失或过期（守护进程未运行或卡死） |
| FR-004 | `2`：配置已具备，但运行时部件不可用：任务库读不了、worker 命令找不到、已启用通道的凭证缺失 |
| FR-005 | `3`：配置本身不完整或不可用：配置文件缺失、内容无法解析、仓库清单为空、仓库路径不存在、没有启用任何通道 |
| FR-006 | 多类问题同时存在时按 `3 > 2 > 1` 取一个退出码，报告列出全部问题 |
| FR-007 | 守护进程启动后每 30 秒刷新心跳；心跳超过 3 分钟未更新视为过期 |
| FR-008 | 巡检每小时执行一次；正常时无输出、无推送，只把去重记录清零 |
| FR-009 | 异常时按「退出码 + 问题标识集合」去重：与上次通知相同则静默；不同则输出报告，并在配置了通道与投递目标时推送 |
| FR-010 | 推送目标取 `scheduler.chatId`，缺省退到探针的 `chatId`，再退到 webhook 的 `chatId`；都没有时只写日志 |
| FR-011 | 推送失败只写标准错误，不改变退出码 |
| FR-012 | `pisa status --alert` 为巡检入口：正常静默、异常去重后说话；不带 `--alert` 时每次完整输出，供人工查看 |
| FR-013 | 心跳与去重记录都放在状态目录下，进程重启后去重仍有效 |
| FR-014 | 未知参数打印用法并以 `64` 退出，不与四种状态码冲突 |

## 5. 验收

1. 缺配置文件或内容无法解析时 `pisa status` 退出 `3`，报告包含原因；解析失败不得崩溃
2. 配置了不存在的仓库路径时退出 `3`
3. worker 命令不存在、或通道凭证缺失、或任务库损坏时退出 `2`
4. 配置与部件正常但无心跳（或心跳过期）时退出 `1`
5. 全部正常（心跳新鲜、任务库可读）时退出 `0`
6. 同一异常连续巡检两次：第一次输出，第二次静默；恢复后再次异常会重新输出
7. `--alert` 在正常状态下无输出
8. `bun test` 与 `bunx tsc --noEmit` 通过

## 6. 非目标

- 自动修复或自动重启（重启仍由 launchd / supervisor 负责）
- 收集指标、历史趋势、告警分级
- 与 IM 里的 `/pisa status` 任务看板合并（两者受众与输出不同）
- 巡检间隔的配置项（由 launchd 的定时决定）
