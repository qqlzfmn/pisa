# 021 · 槽位与人优先通道

- 状态：draft
- 关联：002-parallel-workers（并发上限）、010-status-board（看板）

## 1. 问题

并发槽位被长任务占满时，人发一条续跑（`continue`）或想看状态，要和新任务一起排到队尾，等几十分钟才有反馈。调度只按 `created_at` 取队首、按活跃 Promise 数判断是否满载，没有区分「谁在等」：人可以等长任务跑完，但自己的追问不该排在后面。

## 2. 目标

- 槽位计数显式：基础槽位 = `worker.concurrency`，人的追问另有备用槽位 = `worker.humanSlots`（默认 1，0 关闭）。
- 人的追问（`continue`，含 PR 评论续跑）在基础槽位满时可使用备用槽位。
- 新任务（普通 launch、定时、webhook 等自动入口）只能用基础槽位，不得插队占用备用槽位。
- `/pisa status` 在满载时仍立即返回，并显示槽位占用与每条排队任务的排队原因。
- 任务结束（成功、失败、取消）立即释放槽位；`resume` 与自动补位走同一套判定。

## 3. 非目标

- 多级优先级队列、抢占正在执行的任务
- 按仓库或用户的独立配额
- 跨进程槽位协调（槽位仍是单守护进程内的事实）

## 4. 用户故事

### US-1 满载时追问能进

作为请求者，两个长任务占满基础槽位，我希望 `continue` 立刻开始，而不是等它们跑完。

- **Given** `concurrency=2`、`humanSlots=1`，两个长任务在跑
- **When** 我发 `/pisa continue <已完成任务号> 再改一处`
- **Then** 续跑任务在下一个调度周期内进入 `running`，总占用 3/3

### US-2 新任务不插队

作为请求者，满载时我发新任务，它应继续排队，不能挤掉或占用人的备用槽位。

- **Given** 基础槽位 2/2 已满，备用槽位空闲
- **When** 我发 `/pisa 新任务`
- **Then** 新任务保持 `queued`，直到有基础槽位空出

### US-3 满载时状态可用

作为请求者，满载时我需要知道为什么任务在排队。

- **Given** 槽位占满
- **When** 我发 `/pisa status`
- **Then** 立即返回看板，含槽位占用与每条排队任务的排队原因

## 5. 功能需求

| ID | 需求 |
| --- | --- |
| FR-001 | 槽位分 `base` 与 `human` 两类，容量分别为 `worker.concurrency`（最小 1）与 `worker.humanSlots`（默认 1，最小 0）；总容量为两者之和 |
| FR-002 | 任务创建时确定车道并落库：人的续跑为 `human`，其余为 `base` |
| FR-003 | 补位按 `created_at` 扫描 `queued`：`base` 车道要求占用 < `concurrency`；`human` 车道要求占用 < `concurrency + humanSlots`；前者不满足时跳过该任务继续为后者补位 |
| FR-004 | `base` 车道任务在占用 ≥ `concurrency` 时保持 `queued`，不得使用备用槽位 |
| FR-005 | 槽位占用以进程内显式计数维护，任务结束立即释放；`resume` 使用任务原车道判定 |
| FR-006 | 看板输出槽位行（基础占用/上限、备用占用/上限）与每条排队任务的排队原因 |
| FR-007 | 状态查询不占 Worker 槽位，满载时仍立即响应 |

## 6. 验收

1. `concurrency=1`、`humanSlots=1`，一个长任务在跑时续跑任务进入 `running`，新任务保持 `queued`
2. 长任务结束后新任务补位；占用回落到基础槽位
3. `/pisa status` 在满载时立即返回，含 `槽位：` 行与 `等槽位（…）` 的排队原因
4. `humanSlots=0` 时行为与改造前一致：所有任务共用 `concurrency` 个槽位
