# 011 · GitHub 评论多仓库轮询

- 状态：implemented
- 关联：006（PR 评论绑定）、007（Issue 评论绑定）把单仓库轮询做完，这里只扩充仓库维度
- 依赖：006 的轮询/去重/回帖机制；008 的本地仓库别名不参与 GitHub 路由

## 1. 问题

006 / 007 的 watcher 只监听一个仓库：`github.repo` 是单个字符串，`since` 是一条全局下界，任务去重 id 和 PR 匹配也都不带仓库维度。维护多个仓库时只能部署多份 pisa，或者反复改配置重启。更糟的是 PR / Issue 编号在每个仓库里各自从 1 开始：同一个 `#12` 在两个仓库指向完全不同的 PR，单仓库模型会把它们混成一个任务、把回帖发到错误的仓库。

## 2. 目标

- 一份配置监听多个 GitHub 仓库，各自独立轮询、独立增量下界
- 单个仓库失败（拉取、类型判定、投递）只影响它自己，不推进它的下界，也不影响其它仓库
- 事件去重、PR → 任务匹配、回帖目标都带上仓库维度
- 旧配置（`repo` + `chatId` + `userId`）继续可用，行为不变

## 3. 用户故事

### US-1 一份进程看多个仓库

作为维护者，我在 `github.repos` 里列出三个仓库，pisa 用一份进程分别监听，各自的评论都能派活。

### US-2 一个仓库 429 时不拖累其它仓库

作为维护者，仓库 A 的拉取被限流，仓库 B、C 的评论仍按轮次处理；A 恢复后从失败前的位置继续，不漏评论。

### US-3 同名 PR 号不串仓库

作为维护者，`o/a#7` 与 `o/b#7` 是两个不同的 PR。A 的评论续跑 A 的任务、回帖到 A；B 同理。

### US-4 回帖回到评论所在的仓库

作为评审人，我在 `o/b` 的 PR 下评论，任务完成后回复出现在 `o/b`，不会跑到 `o/a`。

## 4. 需求

| ID | 需求 |
| --- | --- |
| FR-001 | `github` 新增可选 `repos: Array<{ repo: string; chatId: string; userId: string }>`；旧的 `repo` / `chatId` / `userId` 仍可单独使用 |
| FR-002 | 仓库清单归一化：`repos` 非空时优先使用；否则由 `repo` + `chatId` + `userId` 组成单元素数组。两者都没有时不监听任何仓库 |
| FR-003 | `since` 按仓库维护并落库（`meta` 表 `github:since:<repo>`，值为 ISO 时间）；每个仓库缺失记录时以启动时刻初始化并落库，重启后从落库值继续 |
| FR-004 | 每轮逐仓库轮询；某个仓库的拉取或类型判定失败时，只跳过该仓库本轮剩余处理，不推进它的 `since`，继续处理其它仓库 |
| FR-005 | 单个仓库的投递异常只记日志并保留该仓库的 `since`，不中断本轮其它仓库 |
| FR-006 | 事件 id 带仓库：`github:comment:<repo>:<id>`。同一评论 id 出现在不同仓库时视为两个事件 |
| FR-007 | 投递时把所属仓库写入 `IncomingMessage.replyRepo`，任务落库到 `tasks.reply_repo` |
| FR-008 | `store.taskByPr(pr, repo?)`：带 `repo` 时只匹配 `pr_url` 包含 `github.com/<repo>/pull/<n>` 的成功任务；不带 `repo` 时保持旧行为（任意仓库中该编号的最新成功任务） |
| FR-009 | `Task` 新增 `replyRepo: string | null`；表新增列 `reply_repo`，老库启动时补列 |
| FR-010 | 回帖（PR 与 Issue）使用 `task.replyRepo ?? github 配置中的单仓库`（归一化后的第一个仓库）；两者都没有时不回帖 |
| FR-011 | 旧配置不出现 `repos` 时，轮询、去重、回帖的全部外部行为与 006/007 一致，只有事件 id 变为带仓库前缀 |
| FR-012 | 启动日志列出实际监听的仓库清单 |

## 5. 验收

1. 给定 `repos` 为 `o/a` 与 `o/b`，两个仓库各有一条 `/pisa` 评论，一轮轮询后产生两个任务，`replyRepo` 分别为 `o/a`、`o/b`
2. 给定两个仓库的评论 id 相同，一轮轮询后仍产生两个任务（事件 id 含仓库）
3. 给定同一轮返回相同评论，连续两轮轮询后任务数不变（按 `github:comment:<repo>:<id>` 去重）
4. 给定 `o/a` 拉取失败、`o/b` 正常，本轮只为 `o/b` 建任务；下一轮 `o/a` 恢复后，其查询下界仍是启动时刻（失败轮未推进）
5. 给定 `o/a#7` 与 `o/b#7` 各有成功任务，`taskByPr(7, "o/a")` 与 `taskByPr(7, "o/b")` 分别返回对应任务；`taskByPr(7)` 返回最新的成功任务
6. 给定任务 `replyRepo = "o/b"`，任务成功后向 `o/b` 的 PR / Issue 回帖，`gh` 参数里的 `--repo` 为 `o/b`
7. 给定任务 `replyRepo = null` 且配置为旧的单仓库写法，回帖仍用 `github.repo`
8. 给定配置只有旧的 `repo` / `chatId` / `userId`，评论产生任务的 `chatId`、`userId` 与 PR / Issue 绑定与改造前一致
9. 给定 `repos` 为空数组且没有旧字段，启动不轮询、不报错

## 6. 非目标

- GitHub 仓库到本地 `repos` 别名（工作副本路径）的自动映射：配置里没有映射信息，GitHub 评论仍落在默认本地仓库
- 每个仓库独立的轮询间隔、token 或并发策略：间隔与 token 仍在 `github` 段全局配置
- 跨仓库迁移任务或 PR：一个任务始终属于一个仓库
- webhook、定时任务、主动发现的仓库维度（各自已有来源）
- 评论作者鉴权：投递身份仍由各仓库条目或旧字段的 `userId` 决定
