# 022 · Worker 槽位与人类优先通道

- 状态：implemented
- 关联：002-parallel-workers（并发上限；本文改掉它「任务优先级插队」这一非目标）、010-status-board（看板）、017-task-stages（阶段投影）、005-crash-resume（`resume` 的并发判定）
- 依赖：无

## 1. 问题

`worker.concurrency`（默认 2）是唯一的并发闸门，`Router.fill()` 严格按 `created_at` 先来先跑。闸门只认「槽位有没有空」，不认「谁在等」：人的一句追问和新开一个任务，在它眼里完全一样。

证据（改动前）：

- `src/router.ts` 的 `fill()` 只做 `while (this.active.size < limit)` + `store.nextQueued()`，没有任何优先级；`active` 是 `Map<taskId, Promise>`，槽位是隐式的，看不出来也不可配置。
- `src/router.ts` 的 `handleResume()` 在 `this.active.size >= limit` 时直接回「当前并发已满（2），稍后再恢复」，人连排队都排不上。
- 复现（concurrency=1、一个长任务占住槽位）：

```
运行中
t_...b07c82 · working（执行中） · demo · 已运行 0s · 长任务

排队（1）
t_...45368f · working/queued（等空闲槽位） · demo · 追问一句
```

追问任务恒定 `queued`，看板不显示槽位用量，也不说在等哪一类槽位；只有等长任务真正结束才会动。长任务跑几十分钟，追问就等几十分钟。

## 2. 目标

- 槽位显式化：工作槽 = `worker.concurrency`，另加固定的 1 个追问槽；用量可从看板直接读出
- 人的追问（`continue`、`resume`、评论续跑）可以被一个长任务挡在外面时仍然立刻开跑
- 新派的任务不插队：工作槽占满时一律排队
- 排队要说明在等哪一类槽位，而不是笼统的「等空闲槽位」
- 追问槽不新增配置项，行为在并发被调成任意值时都成立

## 3. 用户故事

### US-1 长任务中追问

作为请求者，一个长任务正在跑（并发已满），我发 `/pisa continue <任务号> 追问一句`，希望在长任务结束前就看到结果，而不是等几十分钟。

### US-2 新任务不插队

作为请求者，我在并发满时新派一个完全无关的任务，接受它排在后面：抢占已有工作的是人的追问，而不是又一单新活。

### US-3 恢复中断任务

作为请求者，我要 `resume` 一个被重启打断的任务，并发满时希望它和追问一样能挤进追问槽，而不是被直接拒绝。

### US-4 看板读者

作为看板读者，我在 `/pisa status` 第一行看到 `槽位：工作 1/1 · 追问 +0/1`，在排队的任务行看到「排队原因：追问槽位已满」，知道谁卡住了。

## 4. 需求

| ID | 需求 |
| --- | --- |
| FR-001 | 槽位分两类：**工作槽** 上限 `worker.concurrency`（缺省 2，最小 1）；**追问槽** 固定 1 个，不可配置。任务同时在跑的上限为工作槽 + 追问槽 |
| FR-002 | 任务新增 `priority` ∈ `auto` / `human`，落库列 `priority`（`TEXT NOT NULL DEFAULT 'auto'`），旧库在 `Store` 构造时补列 |
| FR-003 | `human`：`/pisa continue`、`pisa continue`、带 `continueFrom` 的评论续跑。其余入口（`/pisa <需求>`、`pisa task`、cron、webhook、探针）一律 `auto`。线程内的补充消息（`attachThreadNote`）不建任务、不占槽位 |
| FR-004 | 补位规则：工作槽有空位时按创建时间先来后到，任何任务都不能插队；工作槽占满后，只有 `human` 任务能用追问槽。`auto` 永远不会进追问槽 |
| FR-005 | `resume` 的上限改为 工作槽 + 追问槽；满时回执写明当前槽位用量，不再只说「并发已满（n）」 |
| FR-006 | `/pisa status` 与 `pisa status` 首行输出 `槽位：工作 <占用>/<上限> · 追问 +<占用>/<上限>` |
| FR-007 | 排队段的任务行在确实卡住时追加 `· 排队原因：<工作槽位已满\|追问槽位已满>`；有容量、下个调度周期就会开跑时不追加 |
| FR-008 | 阶段投影不变：`queued` 仍是 `working/queued（等空闲槽位）`，具体等哪类槽位由排队原因回答，不改 017 的规则表 |
| FR-009 | 槽位按运行中任务数实时计算，不预占、不落库；数据库不新增槽位表 |

追问槽固定 1 个而不是「若干」：它要救的是「人问一句」这一种情形，两个并发追问同时存在的价值远低于把机器压垮的风险；并发调高时工作槽自动变大，追问槽保持 1 个。

「插队」指的是占用追问槽，不是把排队中的任务往后挤：工作槽的先后顺序保持先来后到，长任务占满工作槽之后，追问不必等工作槽释放。

## 5. 验收

1. `worker.concurrency = 1`，一个长任务在跑时发 `/pisa continue <父任务> 追问`：追问任务立刻 `running`，与长任务并行（两个 worker 同时执行），看板运行中两行
2. 同一时刻新派 `/pisa 另一个任务`：状态仍是 `queued`，不会开跑
3. 长任务 + 一个追问已占满工作槽与追问槽时，再发第二条 `continue`：仍 `queued`，看板排队行带「排队原因：追问槽位已满」
4. `/pisa status` 首行出现真实槽位用量（如 `槽位：工作 1/1 · 追问 +1/1`）
5. 工作槽已满、追问槽空时 `resume` 一个 `paused` 任务：成功并进入追问槽；两者都满时回执含槽位用量
6. `bun test` 与 `bunx tsc --noEmit` 通过

## 6. 非目标

- 不新增 `worker.humanConcurrency` 之类的配置项，追问槽数量固定为 1
- 不做按仓库、按用户的槽位配额
- 不支持手动提升已排队任务的优先级，也不做 priority 的排队重排 UI
- 不改 Web 控制台的表格与详情面板（`/api/tasks`、阶段字段均不变）
- 不改阶段规则表、不改 SQLite 现有列语义
- 不改变 `merge` 在运行中任务存在时的拒绝策略
