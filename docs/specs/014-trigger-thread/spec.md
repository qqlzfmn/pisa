# 触发器幂等与线程归属

## 目的

pisa 现在只用事件标识（`eventId`）去重：同一事件重复投递被静默丢弃，编辑过的消息因为标识不变被当成重复丢弃，同一件事从不同入口进来会各建一个任务。回复续跑靠「聊天 + 消息」绑定，入口换了就找不到父任务。

本规格把「一条触发」从任务身上剥离出来，单独落表，让去重、编辑、线程归属有唯一的数据依据。

## 术语

- 触发（trigger）：一次入口事件，例如一条 Telegram 消息、一条 GitHub 评论、一次定时触发、一次 webhook 调用。
- 线程键（thread_key）：入口给出的会话标识。同一线程内的消息可归到同一个任务。
- 正文摘要（payload_hash）：触发正文的稳定摘要，用于判断「同一条消息的编辑版」。
- 版本（version）：同一触发标识下正文的修订序号，从 1 开始。

## 需求

### FR-001 触发器记录

每次入口事件落一条触发器记录，字段固定为：事件标识 `id`、入口 `source`、线程键 `thread_key`、发起人 `actor`、触发时间 `at`、正文摘要 `payload_hash`、版本 `version`、归属任务 `task_id`。同一 `id` 下 `version` 单调递增，记录只增不改。

### FR-002 重复触发返回已有任务

同一 `id`、同一正文摘要重复到达时，返回该触发已归属的任务，不新建任务，并对发起人回执「已接单」与任务号。不再静默丢弃。

### FR-003 同一线程归并

不同事件标识但同 `thread_key`、同 `actor`、同 `payload_hash`，且已有任务未结束（排队中、执行中、暂停）时，视为同一请求，返回已有任务。

### FR-004 编辑消息按版本区分

同一 `id`、正文摘要变化时：不新建任务，写入 `version + 1`。若归属任务仍在排队，任务正文更新为最新版本；其他状态把新正文记为任务上下文。

### FR-005 线程归属与回复续跑

入口为消息提供线程键。回复某条消息时，父任务解析顺序为「该消息绑定的任务」→「同一线程内同发起人最近的任务」；父任务已结束则走续跑，父任务仍在排队或执行中则把回复正文记为它的上下文。

### FR-006 迁移不丢数据

启动时把已有任务回填为触发器记录：`id` 取任务的事件标识，线程键按入口还原，正文摘要取已保存的任务正文。迁移幂等，任务数据不变。

### FR-007 不同线程互不归并

同正文、不同 `thread_key` 的触发各自成任务。

### FR-008 去重来源唯一

触发器表是去重的唯一依据；任务不再依赖「聊天 + 消息」绑定判断是否重复。

### FR-009 上下文持久化

记为上下文的补充内容写进任务，后续读取任务时可见；执行中的任务在下一轮开始时读取到。

## 验收

1. 触发器表记录 `id`、`source`、`thread_key`、`actor`、`at`、`payload_hash`。
2. 重复触发返回已有任务，不新建。
3. 同一线程的后续消息可路由到现有任务，或记为上下文。
4. 旧 `tasks` 回填为触发器记录，任务数据不丢。
5. 测试覆盖：重复投递只 1 个任务；不同线程 2 个任务；编辑消息按版本区分。

## 不做

- 跨进程去重协调：单进程单库即可满足。
- 追溯历史任务被编辑前的正文：回填只能使用已保存的任务正文。
- 编辑后自动取消或回滚已开始的执行。
