# 018 · 残留对账与清理

- 状态：implemented
- 关联：013（rewind）、005（崩溃恢复）、015（Web 控制台）

## 1. 问题

回退目前只有 `rewind`，且必须逐个任务手工执行；任务失败或中断留下的资源没有核对入口。

已确认的残留来源（读代码得出，非推断）：

- **取消暂停任务只改状态**。`src/router.ts` 的 `handleCancel` 对 `queued`/`paused` 直接 `transition(..., "cancelled")`，不删工作副本与分支；`paused` 任务两者都在，取消后就成了无人引用的资源。
- **失败只清本地、不清远程**。`runTask` 失败路径调用 `dropWorktree` 与 `cleanupBranch`，后者只删本地 `pisa/<id>` 分支并清账本；推送与建 PR 经 outbox 异步执行，任务可能在 push 或 PR 成功之后才失败，远程分支与开放 PR 留在 GitHub。
- **成功路径的工作副本可能残留**。`dropWorktree` 依赖 `git worktree remove` 成功；目录被占用或删除失败时没有补偿，任务已是 `succeeded`，不会再被处理。
- **任务行被清理后资源成孤儿**。`retention.ts` 明确不删任务行，但手工删库、迁移或恢复备份后，磁盘上的 `pisa/` 分支、`worktrees/<id>` 与开放 PR 找不到对应记录。
- **暂停任务的工作副本被手工删掉**后没有提示，`resume` 会失败。

影响：磁盘与 GitHub 上累积无用分支与 PR，排查时无法区分「还在用的」和「可以删的」，只能靠人记任务号逐个 `rewind`。

## 2. 目标

- 一个显式入口核对任务记录与仓库现状：本地分支、远程分支、工作副本、开放 PR
- 远程分支以 `git ls-remote --heads origin` 为准，不依赖可能过期的远端跟踪引用；查询失败时跳过远程判断并在输出里说明
- 默认只读；`--fix` 才清理，且只清理已结束任务与孤儿资源
- 运行中（`queued`/`running`/`paused`）与成功的任务资源不动
- 清理成功后同步删账本，避免后续 `rewind` 重复处理

## 3. 用户故事

### US-1 每周清理的维护者

我发 `/pisa reconcile` 看全局差异，确认没有误报后加 `--fix` 清掉失败任务留下的远程分支与 PR。

### US-2 排查单个任务的执行者

某个任务的消息对不上，我发 `/pisa reconcile t_xxx` 只看这个任务，确认分支与工作副本是否还在。

### US-3 暂停任务的主人

`resume` 前发一次对账，知道工作副本已丢，就不会白试一次恢复。

## 4. 需求

| ID | 需求 |
| --- | --- |
| FR-001 | `/pisa reconcile` 扫描全部任务；带任务号只核对该任务，不扫描全局孤儿 |
| FR-002 | 输出任务记录与本地分支、远程分支、工作副本、开放 PR 的差异；只列有差异的资源与有意保留的资源 |
| FR-003 | `--fix` 清理已结束（`failed`/`cancelled`/`rewound`）任务的自建分支、遗留工作副本与仍打开的 PR |
| FR-004 | `--fix` 全局清理任务表里查不到的 `pisa/` 分支、`worktrees/<id>` 目录与开放 PR |
| FR-005 | `queued`/`running`/`paused` 的资源一律保留；`succeeded` 的分支与 PR 保留，遗留工作副本可清理 |
| FR-006 | 共用分支（`task.branch !== pisa/<该任务号>`）与仍被未结束/成功任务引用的分支不删 |
| FR-007 | 清理顺序：工作副本 → 本地分支 → 关闭 PR → 远程分支；先关 PR 再删它的头分支，避免 PR 被 GitHub 自动关闭后 `gh pr close` 报错；逐条执行，失败不中断 |
| FR-008 | 清理成功的项从账本删除（worktree/branch/push/pr）；失败项保留并提示重试 |
| FR-009 | `gh` 不可用或查询失败时跳过 PR 核对并说明，不误删分支 |
| FR-010 | 不做后台自动清理；只有显式命令会改动资源 |

## 5. 验收

| 场景 | 预期 |
| --- | --- |
| 失败任务的本地/远程分支、工作副本、开放 PR | 预览列为可清理；`--fix` 后四者消失，账本对应行删除 |
| 取消的暂停任务 | 工作副本、本地分支、远程分支清理 |
| 运行中/暂停中的任务 | 资源保留；暂停任务缺工作副本时只报告，不清理 |
| 成功任务 | 分支与 PR 保留；多出的工作副本可清理 |
| 共用分支、仍被成功任务引用的分支 | 保留并说明原因 |
| 任务表无记录的分支/工作副本/PR | 全局 `--fix` 清理 |
| 带任务号的 `--fix` | 只动该任务的资源 |
| `gh` 查询失败 | 输出「PR 未核对」，分支处理继续 |

## 6. 取舍

- **不复用 `rewind`**：`rewind` 的语义是「撤销这条任务的交付」，面向单任务且会改变任务状态；对账面向资源集合，包含没有任务行的孤儿，也不能把别人的任务改成 `rewound`。两者共用 `git`/`gh` 封装，但计划与文案分开。
- **不做自动清理**：残留判定存在误伤风险（例如人工在 `pisa/` 前缀下建的分支），只由人显式触发；与 `rewind` 的「预览 + --yes」一致，改为两段式 `reconcile` / `reconcile --fix`。
- **`pisa/` 前缀才认孤儿**：手工分支不动；代价是前缀内的人工分支会被当成孤儿。
- **成功任务的工作副本可清理**：成功路径本应删除工作副本，存在即残留；分支与 PR 才是交付物。
- **失败任务的分支可清理**：失败分支原设计「保留供排查」，现在由人决定：先预览确认不再需要，再 `--fix`。
- **`--fix` 不做权限分层**：入口已在通道白名单内，且只动已结束任务与孤儿；清理失败任务的分支不再等于回退别人的代码。
