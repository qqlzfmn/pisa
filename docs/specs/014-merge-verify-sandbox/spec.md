# 014 合并前验证的最小权限执行

## 1. 背景

`/pisa merge` 在验证副本里执行 `bun test`，验证副本的内容来自 Worker 写的代码与测试。这条路径在自举场景下是合入主干前唯一的闸门，因此它执行的代码不可信。

当前实现有两个问题：

1. 验证命令继承 pisa 进程的完整环境变量，包括 `GH_TOKEN`、`PISA_TELEGRAM_TOKEN` 等凭据。Agent 只需在测试里读取环境变量，就能以 pisa 身份拿到凭据。
2. 验证命令没有超时。一个死循环或长时间 `sleep` 会永久挂住 `handleMerge`，之后的合并命令全部排队。

## 2. 用户故事

### US-1 合入主干前的验证不泄露凭据（P0）

作为运维者，我希望验证命令看不到 pisa 的凭据，这样 Worker 写的测试无法窃取 token。

验收场景：

- **Given** pisa 进程环境里有 `GH_TOKEN`
- **When** 任务分支的测试读取 `process.env.GH_TOKEN`
- **Then** 测试看不到该值，回执文本也不出现任何 token 明文

### US-2 验证不会把合并流程挂死（P0）

作为请求者，我希望验证超时后自动失败返回，这样一条坏测试不会让合并命令失去响应。

验收场景：

- **Given** 任务分支里有一个耗时 30 秒的测试，验证超时配置为 2 秒
- **When** 请求者执行 `/pisa merge <任务号>`
- **Then** 2 秒左右收到「未合并 · 验证超时」，主干没有任何新提交

## 3. 功能需求

| ID | 需求 |
| --- | --- |
| FR-001 | 验证命令只拿到执行测试必需的最小环境，不继承 pisa 进程的凭据与配置 |
| FR-002 | 验证超时默认 600 秒，可通过 `worker.verifyTimeoutSec` 配置；到时终止验证进程 |
| FR-003 | 超时后回执写明「未合并 · 验证超时」，不合入主干，不留下验证副本与验证分支 |
| FR-004 | 验证失败的输出（含超时说明）经过脱敏后再进回执 |
| FR-005 | 验证通过后的合并行为、账本记录与看护重启行为保持不变 |

## 4. 非功能需求

| ID | 需求 |
| --- | --- |
| NFR-001 | 最小环境只放行运行测试所需的基础变量（`PATH`、`HOME`、临时目录、语言区域），其余一律不传 |
| NFR-002 | 超时终止能可靠返回，不依赖测试进程自行响应信号 |

## 5. 非目标

- 不改变 Worker 子进程的环境构造（属于 Worker 侧的最小权限改造）。
- 不做容器级隔离、网络隔离或文件系统隔离。
- 不改变 `bun test` 的命令与测试目录探测规则。

## 6. 验收标准

1. 任务分支放 `tests/slow.test.ts`（`sleep 30s`）、`worker.verifyTimeoutSec` 设为 2：`handleMerge` 5 秒内返回「未合并 · 验证超时」，`git log main` 无新提交。
2. 任务分支的测试打印 `process.env.GH_TOKEN`：回执不出现 token 明文，且测试可观察到该变量不存在。
3. 现有 `bun test` 与 `bunx tsc --noEmit` 全绿。
