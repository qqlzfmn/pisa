# 016 · 来源准入与策略版本

- 状态：implemented
- 关联：`seed:policy-admission`
- 依赖：无

## 1. 问题

现在谁能派活由 `whitelist.users` 一处决定，所有入口共用，且只在收到消息那一刻校验：

- **入口权限没有区别**：本地 CLI、Telegram、webhook、GitHub 评论、cron 共用同一张用户名单。只想放开 webhook，就要把 webhook 的请求者加进白名单，这同时放开了聊天与 CLI；只想收紧某个来源，也做不到。
- **没有「点名才接」的档位**：被动发现（群关键词）与人工触发走同一判定。想让群里只有点名或带触发词的消息接单、闲聊不接单，只能整个关掉或整个放开。
- **没有观察模式**：想先看清「按新规则会接哪些活」再真正执行，没有手段；改完即生效，出问题只能回滚配置。
- **配置变更不可追溯**：任务只记录请求者，没记录建单时凭什么放行（来源、名单内外、是否点名、命中哪一格）以及当时的策略版本。事后看到一条跑过的任务，无法判断它按哪版规则进来。
- **恢复不重校验**：暂停任务恢复时只看原请求者，不看当前策略。降权之后（移出白名单、关掉某个来源），他先前暂停的任务仍可恢复执行。

## 2. 目标

- 谁能从哪个入口派活，按来源分别配置；改一个来源不影响其他来源。
- 「名单内/名单外」与「点名/未点名」四个组合各自可放行或拒绝。
- 新规则可以先用观察模式看判定结果，再切自动执行。
- 每条任务留下准入凭据与策略版本；配置变更不追溯已建立的任务。
- 恢复暂停任务前按当前策略重校验，拒绝时说明原因与版本差异。
- 当前放行面能一条命令查到，包括策略版本。

## 3. 用户故事

### US-1 按来源分别放行

作为运维者，我可以只让某个入口停止接单，而不影响其他入口。

- Given 某来源的 `allowed` 为 false，When 从该来源派活，Then 不建任务，回执说明来源未开放。
- Given 只有 GitHub 评论的 `allowed` 为 false，Then Telegram、webhook、CLI 的正常派活不受影响。

### US-2 名单内外与点名分别取舍

作为运维者，我能决定「不在白名单但点名了 pisa 的人」是否接单，而白名单内的人保持常态。

- Given 某来源「名单外 × 点名」为放行，When 名单外用户点名派活，Then 建任务并记录命中的准入格。
- Given 该格为拒绝，When 同样的请求到达，Then 不建任务，回执说明名单外且未获准入。
- Given 被动发现的消息（群关键词命中，未点名），Then 按「未点名」列判定，与人工点名触发互不影响。

### US-3 观察模式先看后开

作为运维者，我想先看判定结果再决定是否真的执行。

- Given 某来源处于观察模式，When 名单内用户派活，Then 不建任务、不执行，回执说明处于观察模式。
- Given 该来源切回自动，When 同样的请求到达，Then 正常建任务并执行。

### US-4 任务带上准入凭据

作为事后排查的人，我能从任务记录里看出它是按哪版策略、命中哪一格进来的。

- Given 任一入口建单，Then 任务记录来源、名单内外、是否点名、命中格、接单模式，以及建单时的策略版本。
- Given 旧版本建的任务没有这些记录，Then 按缺失处理，不影响读取与展示。

### US-5 恢复前重校验

作为运维者，降权之后我希望暂停的任务不再能恢复。

- Given 一个暂停任务，When 当前策略已不允许它的来源或请求者，Then 恢复被拒，回执说明原因与建单/当前策略版本，任务保持暂停。
- Given 策略未变，Then 恢复流程与之前一致。

### US-6 查看当前规则

作为运维者，发一条命令就能看到每个来源的放行面与策略版本。

- Given 发送 `/pisa policy`，Then 回执列出每个来源的 allowed、accept、四个准入格与策略版本。
- Given 非白名单用户发送该命令，Then 被拒。

## 4. 需求

| ID | 需求 |
| --- | --- |
| FR-001 | 每个来源有独立策略：`allowed`、`accept`（off/observe/auto）、四个准入格（名单内/外 × 点名/未点名，各自放行或拒绝） |
| FR-002 | 缺省字段与未知来源落到来源默认值；默认保持现有行为（名单内放行、名单外拒绝、auto）；本地 CLI 是本机受信入口，默认名单内外都放行 |
| FR-003 | 任务记录 mandate（来源、名单内外、是否点名、命中格、接单模式）与建单时的策略版本；旧任务缺这两项时按缺失处理 |
| FR-004 | 策略变更不追溯：已建立的任务按建单时的准入继续执行，不因之后改配置被取消 |
| FR-005 | 恢复暂停任务前按当前策略重校验来源与请求者；拒绝时说明原因与两个策略版本，任务保持暂停 |
| FR-006 | `/pisa policy`（私聊 `/policy`、`策略` 同义）输出每个来源的规则与策略版本；非白名单用户不可见 |
| FR-007 | 被动发现（群关键词）按「未点名」参与判定；人工触发与机器入口（私聊、cron、探针、webhook、GitHub、CLI）按「点名」 |
| FR-008 | 非法 `accept` 值或未知字段不让启动失败：回落到默认并告警；拒绝原因以「无权限」开头，Web 控制台据此判失败 |

## 5. 验收

1. `pisa.config.json` 的 `policy.<来源>` 可配 `allowed`、`accept`、`admission`；未配置来源按默认值
2. 测试覆盖：名单外未点名被拒、名单外点名放开后接单、观察模式不建任务、`allowed` 关闭拒单、降权后恢复被拒、改配置后已排队任务仍执行、`/pisa policy` 输出含版本与四个准入格
3. 恢复被拒的回执同时出现建单版本与当前版本
4. `bun test` 与 `bunx tsc --noEmit` 通过

## 6. 非目标

- **仓库白名单不变**：`whitelist.repos` 是仓库级准入，与来源无关，不并入本 feature。
- **策略热加载**：改配置仍需重启进程。
- **完整策略快照**：只记版本哈希与命中格，不存整份策略表。
- **按任务粒度的临时授权**：没有需求支撑。
- **Worker 与 guard 行为**：本 feature 只改准入判定与记录。
