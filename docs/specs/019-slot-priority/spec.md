# 019 · Worker 槽位与人类优先通道

- 状态：implemented
- 关联：002（并发与排队）、010（看板）、017（任务阶段）
- 依赖：002 已交付

## 1. 问题

`worker.concurrency` 是唯一的进程级上限，所有任务排同一条先进先出队列。两个长任务占满槽位时，人对已交付任务的追问（`continue`）只能排在新任务后面，常常要等几十分钟才能开始；看板也只显示「排队」，看不出是在等任务槽位还是等人类追问槽位。

## 2. 目标

- 槽位显式化：普通任务槽与人类追问槽各有一个独立上限，计数可见
- 人的追问（`continue`）不排在长任务后面：普通槽占满时仍可用自己的额外槽位开始
- 新任务（launch）不占用人类追问槽，不插队
- `status` 显示两条槽位的占用/上限，排队任务标注排队原因

## 3. 非目标

- 抢占正在执行的任务
- 按优先级重排普通任务队列（普通任务仍然先进先出）
- 跨进程/多副本的槽位协调（沿用单机语义）

## 4. 用户故事

### US-1 满槽时追问

作为请求者，两个长任务占满普通槽位后，我 `continue` 已交付的任务，希望它立刻开始。

- **Given** `worker.concurrency=2`、`worker.humanConcurrency=1`，两个普通任务在跑
- **When** 我发 `continue <任务号> <新要求>`
- **Then** 新任务进入 `running`，普通任务不受影响

### US-2 新任务仍排队

作为请求者，我在满槽时发一条新需求，它应保持排队，不占人类追问槽。

- **Given** 两个普通任务在跑，人类追问槽也已被一条追问占用
- **When** 我发一条新任务
- **Then** 它保持 `queued`，直到普通槽位空出

### US-3 看到排队原因

作为维护者，我看 `status` 时能知道每个槽位的占用与上限，以及排队任务在等哪个槽位。

## 5. 需求

| ID | 需求 |
| --- | --- |
| FR-001 | `Task` 增加持久字段 `priority`：`normal`（默认）或 `human`；旧库升级时补列并默认 `normal` |
| FR-002 | `worker.humanConcurrency` 配置人类追问槽上限，默认 1，最小 0；普通槽沿用 `worker.concurrency`（默认 2，最小 1） |
| FR-003 | IM 回复续跑与 `/pisa continue`（含 CLI `pisa continue`）产生的任务为 `human`；GitHub 评论续跑、新任务、定时任务、webhook 均为 `normal` |
| FR-004 | 调度按槽位补位：普通槽只取 `priority=normal` 的排队任务，人类槽只取 `priority=human`；两条槽各自不超过自己的上限 |
| FR-005 | 人类追问不消耗普通槽，新任务不使用人类槽：普通槽占满时新任务必须继续排队 |
| FR-006 | 看板首行输出 `槽位：任务 <used>/<limit> · 人类追问 <used>/<limit>`；`status --json` 输出同样结构 |
| FR-007 | 排队任务在看板行尾追加 `· 原因：任务槽位已满（x/y）` 或 `· 原因：人类追问槽位已满（x/y）` |
| FR-008 | `resume` 按任务所属槽位判断容量，满时说明是哪个槽位已满 |

## 6. 验收

1. `concurrency=2` 且两个普通任务在跑时，`continue` 的新任务进入 `running`，普通槽计数仍为 2/2
2. 同一场景下发新任务，保持 `queued`，看板显示「任务槽位已满（2/2）」
3. 人类追问槽已满（`humanConcurrency=1`）时第二条追问排队，看板显示「人类追问槽位已满（1/1）」
4. `bun test` 与 `bunx tsc --noEmit` 通过
