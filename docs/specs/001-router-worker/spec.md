# 001 · Router–Worker 最小闭环

- 状态：draft（待澄清项确认后转 approved）
- 关联：README 路线图 P0
- 范围：一个 feature，一次只做这一个

## 1. 问题

编码 Agent 目前绑在单个会话上：接活、执行、回话都在同一个上下文里。P0 要验证一件事——把「接单」和「执行」拆成两层之后，一条真实请求能不能从入口走到可评审的结果，并且全程可见、可追溯、不污染主干。

P0 不追求快，追求**闭环成立**。

## 2. 目标（可度量）

- 一条合规请求从发出到收到「已接单」回执 ≤ 60 秒（p95）
- 从接单到产出结果 ≤ 30 分钟（中等规模代码改动）
- 任务全程只有一个 ID，入口消息、执行日志、最终回执三处可对上
- 执行过程不修改主分支
- 失败任务 100% 有可见原因，不静默消失

## 3. 非目标

- 多 Worker 并行（P1）
- 无人指令时主动发现任务（P2）
- 断线重连与状态恢复（P3）
- 多仓库、多租户、权限分级
- 图形界面、移动端
- 对话式多轮需求澄清

## 4. 角色

- **请求者**：提交任务的人，关心「有没有接、做到哪、结果在哪」
- **Router**：全局入口，负责判定、排队、分派、对外回话
- **Worker**：执行者，拥有独立上下文，只对当前任务负责

## 5. 用户故事

### US-1 接单可见

作为请求者，我发出任务后要立刻知道系统收到了。

- **Given** 白名单用户在白名单仓库新建一条带触发词的请求
- **When** Router 收到该事件
- **Then** 60 秒内在原对话回复「已接单 · 任务号 · 预计步骤」，任务状态置为 `running`

### US-2 执行隔离

作为仓库维护者，我不希望 Agent 的工作影响主干和别人。

- **Given** 任务已接单
- **When** Worker 开始执行
- **Then** 它在独立工作副本中操作，主分支无任何变化；所有命令、工具调用、文件改动记入该任务日志

### US-3 结果可评审

作为请求者，我要拿到能直接看的东西，而不是一段「我改好了」。

- **Given** Worker 完成执行
- **When** 存在代码改动
- **Then** 在原对话回复：改动摘要、涉及文件清单、验证结果、变更请求链接
- **And** 无代码改动时，回复结论与依据，不生成空变更

### US-4 失败可见

作为请求者，任务失败时我要知道卡在哪。

- **Given** Worker 执行失败、超时或被中止
- **When** 任务结束
- **Then** 原对话收到失败原因与最后一步操作，状态为 `failed`，不产生变更请求

### US-5 越权拒绝

作为仓库维护者，我不希望任何人能驱动 Agent。

- **Given** 非白名单用户触发
- **Then** 不执行任务，回复一次「无权限」，同一用户 24 小时内不重复提示

### US-6 取消

作为请求者，我发错了要能收回。

- **Given** 任务处于排队或执行中
- **When** 原请求者发出取消指令
- **Then** 任务在 30 秒内停止，状态 `cancelled`，原对话收到确认；已产生的临时改动被清理

## 6. 功能需求

| ID | 需求 |
| --- | --- |
| FR-001 | 接收入口事件（新建请求、追加评论），按事件唯一标识去重 |
| FR-002 | 触发判定：必须同时满足「白名单用户」「白名单仓库」「触发词」三个条件 |
| FR-003 | 任务实体：任务号、来源、请求者、原始请求文本、状态、创建/开始/结束时间、结果、失败原因 |
| FR-004 | 状态机：`queued → running → succeeded \| failed \| cancelled`；禁止非法跃迁 |
| FR-005 | P0 单 Worker：同一时刻最多一个任务执行，其余排队，先到先执行 |
| FR-006 | 接单回执、完成回执、失败回执三种固定格式，均包含任务号 |
| FR-007 | 工作区隔离：每个任务独立工作副本，任务结束（成功或失败）后按策略清理 |
| FR-008 | 结构化日志：每行含任务号、时间、阶段、动作；身份信息与密钥脱敏 |
| FR-009 | 取消指令由原请求者发起才生效 |
| FR-010 | 幂等：同一事件重复投递、进程重启后重复消费，都不产生第二个任务 |
| FR-011 | 超时：单任务默认上限 60 分钟，到时强制终止并进入 `failed` |
| FR-012 | 任务记录持久化，重启后可查询历史任务 |

## 7. 非功能需求

| ID | 需求 |
| --- | --- |
| NFR-001 | 接单回执 p95 ≤ 60 秒 |
| NFR-002 | 任务日志保留 ≥ 30 天，可按键任务号检索 |
| NFR-003 | 重启后不产生重复变更请求（幂等验证） |
| NFR-004 | 默认禁止破坏性操作：强推、重置主干、删除未提交改动 |
| NFR-005 | 单任务失败不影响后续排队任务执行 |

## 8. 边界与约束

- P0 面向单人使用，不做组织级权限模型
- 入口只有一个渠道（见待澄清 C-1）
- 不自动合并变更，只产出待评审结果
- 所有密钥来自环境变量，不落盘

## 9. 假设

- A-1：P0 入口是 Telegram 私聊或群聊消息（IM 通道），产出落在代码托管平台
- A-2：P0 只服务一个仓库
- A-3：Router 与 Worker 跑在同一台机器上
- A-4：触发词可配置，默认 `/pisa`

## 11. 验收

P0 完成时，以下场景全部按 SDD `quickstart.md` 跑通：

1. 白名单用户提需求 → 60 秒内接单回执，任务号可见
2. Worker 修改代码 → 主分支无改动，独立副本有改动
3. 完成后 → 原对话收到摘要 + 文件清单 + 验证结果 + 变更链接
4. 非白名单用户 → 收到一次拒绝，无任务产生
5. 执行中取消 → 30 秒内停止，状态 `cancelled`
6. 重复投递同一事件 → 只有一条任务记录
7. 杀掉进程重启 → 历史任务可查，无重复结果
